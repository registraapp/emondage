Mise à niveau EKS : la checklist pour passer de 1.31 à 1.34 sans casse

Par Amine, ingénieur DevOps · Mis à jour le 3 novembre 2026

Une mise à niveau EKS se fait une version mineure à la fois : inventaire des API dépréciées et des insights, alignement des nœuds, plan de contrôle, puis nœuds et add-ons, et on recommence pour le saut suivant. Depuis juillet 2026, EKS permet de revenir à la version précédente dans les 7 jours, sous conditions ; pour plusieurs sauts d'affilée ou un cluster critique, un cluster bleu/vert reste le filet le plus sûr.

Pourquoi maintenant

Au 3 novembre 2026, le calendrier EKS laisse peu de marge. La version 1.31 sort du support étendu le 26 novembre 2026, après quoi AWS met à niveau le plan de contrôle d'office, sans préavis. Les versions 1.32 et 1.33 sont déjà en support étendu, facturé 0,60 $ par cluster et par heure au lieu de 0,10 $. La 1.34 quitte le support standard le 2 décembre 2026. Le détail des coûts est dans notre article sur le coût du support étendu EKS. Pour sortir durablement du tarif étendu, la cible raisonnable est 1.35, voire plus : c'est trois ou quatre sauts pour un cluster en 1.31.

La checklist en un coup d'œil

  • Lister les API dépréciées ou supprimées dans les manifestes, les releases Helm et le cluster (pluto, kubent).
  • Lire les upgrade insights EKS et traiter chaque statut ERROR ou WARNING.
  • Vérifier que les nœuds sont sur la même version mineure que le plan de contrôle, et sur une AMI qui existe pour la version cible.
  • Relever les versions compatibles de VPC CNI, CoreDNS, kube-proxy, du pilote EBS CSI et des contrôleurs installés par Helm.
  • Contrôler les PodDisruptionBudgets qui bloqueraient le drainage des nœuds.
  • Vérifier qu'il reste au moins cinq adresses IP libres dans les sous-réseaux du cluster.
  • Jouer la mise à niveau complète sur un cluster de staging, en chronométrant chaque étape.
  • Écrire le plan de retour arrière, et décider avant de commencer : rollback EKS ou bleu/vert.
  • Monter le plan de contrôle d'une version, puis les nœuds, puis les add-ons, puis recommencer.
  • Après la bascule : tests de fumée, mise à jour de kubectl et des pipelines, prochaine échéance dans l'agenda.

1. Inventaire : ce qui va casser

API dépréciées

Le guide de migration des API dépréciées de Kubernetes est la référence. Dans la plage qui nous intéresse, la version 1.32 a cessé de servir flowcontrol.apiserver.k8s.io/v1beta3 pour FlowSchema et PriorityLevelConfiguration ; à la date de rédaction, le guide ne liste pas de suppression d'API dans les versions suivantes. Deux outils font l'inventaire :

# Releases Helm installées, comparées à la version cible
pluto detect-helm -owide --target-versions k8s=v1.34.0

# Manifestes du dépôt (Kustomize, YAML bruts)
pluto detect-files -d ./deploy --target-versions k8s=v1.34.0

# Objets présents dans le cluster courant (kubeconfig actif)
kubent

Pluto lit ce qui est déclaré ; kubent interroge le cluster. Les deux s'appuient sur des listes de règles maintenues à la main : un résultat vide n'est pas une preuve, c'est un indice.

Upgrade insights EKS

EKS analyse lui-même chaque cluster : API dépréciées réellement appelées, décalage de versions entre kubelet et plan de contrôle, compatibilité des add-ons.

aws eks list-insights --cluster-name mon-cluster \
  --filter categories=UPGRADE_READINESS

aws eks describe-insight --cluster-name mon-cluster --id <insight-id>

Deux limites documentées par AWS : les insights se rafraîchissent toutes les 24 heures, et la détection des API dépréciées porte sur une fenêtre glissante de 30 jours. Un client corrigé hier peut donc rester signalé plusieurs semaines ; un CronJob mensuel peut ne jamais apparaître.

Nœuds et AMI

kubectl version
kubectl get nodes -o wide

AWS recommande d'aligner les nœuds sur la version du plan de contrôle avant chaque saut. Point bloquant pour la plage 1.31 à 1.34 : la 1.32 est la dernière version pour laquelle EKS a publié des AMI Amazon Linux 2, et leur publication s'est arrêtée le 26 novembre 2025. Passer en 1.33 impose donc des nœuds Amazon Linux 2023 ou Bottlerocket. Cette migration de système, avec ses scripts user-data et ses agents, mérite son propre test.

2. Add-ons : VPC CNI, CoreDNS, kube-proxy, EBS CSI

Les add-ons EKS ne suivent pas le plan de contrôle. Pour chacun, relevez les versions compatibles avec la version cible :

aws eks describe-addon-versions --addon-name kube-proxy \
  --kubernetes-version 1.34 \
  --query "addons[].addonVersions[].addonVersion" --output text

Puis, après la mise à niveau du plan de contrôle et des nœuds :

aws eks update-addon --cluster-name mon-cluster \
  --addon-name kube-proxy --addon-version <version> \
  --resolve-conflicts PRESERVE

PRESERVE conserve vos modifications de configuration ; OVERWRITE les écrase. Répétez pour vpc-cni, coredns et aws-ebs-csi-driver. Les composants installés hors add-ons, par Helm le plus souvent (AWS Load Balancer Controller, cluster-autoscaler, metrics-server, cert-manager, contrôleur d'ingress), ont leur propre matrice de compatibilité : lisez-la avant le saut, pas après. Le cluster-autoscaler en particulier doit être sur la même version mineure que le cluster.

3. Nœuds : groupes managés, Karpenter, Auto Mode

  • Groupes de nœuds managés : aws eks update-nodegroup-version --cluster-name mon-cluster --nodegroup-name ng-app remplace les nœuds par vagues, selon la configuration maxUnavailable du groupe, en respectant les PodDisruptionBudgets.
  • Karpenter : un nœud est considéré en dérive quand la résolution de amiSelectorTerms de son EC2NodeClass donne une autre AMI ; Karpenter le remplace alors, en passant par l'API d'éviction, donc en respectant les PDB. Les pods annotés karpenter.sh/do-not-disrupt bloquent ce remplacement. Vérifiez aussi que votre version de Karpenter supporte la version Kubernetes cible.
  • EKS Auto Mode : les nœuds sont mis à jour automatiquement après le plan de contrôle, en respectant les PDB.
  • Fargate : les pods existants ne changent pas ; ils prennent la nouvelle version au prochain redéploiement.

4. PodDisruptionBudgets

Un PDB mal réglé bloque le drainage et fait échouer une mise à jour de groupe de nœuds. Cherchez ceux qui n'autorisent aucune interruption :

kubectl get pdb -A

Une colonne ALLOWED DISRUPTIONS à 0 signale soit un minAvailable égal au nombre de réplicas, soit une application déjà dégradée. Le cas typique : un déploiement à une seule réplique protégé par un PDB minAvailable: 1. Passez-le à deux répliques le temps de la bascule, ou acceptez explicitement l'interruption. Ne supprimez pas les PDB « pour que ça passe » : ils sont là pour la production.

5. Une version mineure à la fois

EKS n'accepte qu'un saut de version mineure par mise à niveau : de 1.31 à 1.34, il faut trois cycles complets. Chaque mise à niveau du plan de contrôle prend « plusieurs minutes » selon AWS, ne peut être ni suspendue ni annulée une fois lancée, et demande jusqu'à cinq adresses IP libres dans les sous-réseaux du cluster.

aws eks update-cluster-version --name mon-cluster --kubernetes-version 1.32
aws eks describe-update --name mon-cluster --update-id <update-id>
SautPoint d'attention connu
1.31 → 1.32Fin de flowcontrol.apiserver.k8s.io/v1beta3. Dernière version avec des AMI Amazon Linux 2.
1.32 → 1.33Plus d'AMI Amazon Linux 2 : nœuds en AL2023 ou Bottlerocket obligatoires.
1.33 → 1.34Pas de suppression d'API listée par le guide Kubernetes ; relancer insights et pluto quand même.
1.34 → 1.35Idem ; 1.34 quitte le support standard le 2 décembre 2026.

Entre deux sauts, attendez que les nœuds et les add-ons aient rejoint la nouvelle version et que les tests soient verts. Enchaîner trois plans de contrôle d'affilée en laissant les nœuds en 1.31 est techniquement possible (le kubelet tolère trois versions de retard) mais concentre tout le risque sur la fin.

6. Répétition sur un cluster de staging

La répétition est l'étape qui distingue une mise à niveau tranquille d'une nuit blanche. Elle n'a de valeur que si le staging ressemble à la production : même code d'infrastructure, mêmes charts aux mêmes versions, mêmes add-ons, mêmes types de nœuds. Faute de staging, une copie éphémère créée depuis le même Terraform fait l'affaire. Pendant la répétition :

  • chronométrez chaque étape, pour fixer une fenêtre réaliste ;
  • notez chaque correction de manifeste et poussez-la dans le dépôt, pas à la main dans le cluster ;
  • lancez les tests de fumée après chaque saut, pas seulement à la fin ;
  • testez le retour arrière, au moins une fois.

Attention : le trafic du staging n'est pas celui de la production. Les insights du cluster de production restent la source pour les API réellement appelées.

7. Stratégie de retour arrière

Le retour arrière EKS natif

Depuis juillet 2026, EKS permet de revenir à la version mineure précédente. Les conditions sont strictes : dans les 7 jours suivant la mise à niveau, d'une seule version, uniquement pour un cluster mis à niveau sur place (pas pour un cluster créé dans sa version actuelle), et jamais après une mise à niveau forcée de fin de support étendu.

aws eks update-cluster-version --name mon-cluster --kubernetes-version 1.33

Ce que le retour arrière ne fait pas : il ne touche ni aux add-ons, à rétrograder vous-même, ni aux groupes de nœuds managés ou autogérés, à rétrograder avant le plan de contrôle. Seul Auto Mode rétrograde ses nœuds automatiquement ; Fargate ne le permet pas. Revenir vers une version en support étendu exige de repasser la politique en EXTENDED et relance la facturation à 0,60 $.

Le cluster bleu/vert

Au-delà de 7 jours, pour plusieurs sauts d'un coup ou pour un cluster dont la panne coûte cher, la méthode sûre reste le cluster neuf : on crée le cluster cible dans la nouvelle version, on y déploie tout par GitOps ou par les pipelines, on bascule le trafic progressivement (DNS pondéré, répartiteur de charge), et on garde l'ancien cluster quelques jours. Le prix : un double cluster pendant la transition, et un vrai travail sur les données si des bases ou des volumes persistants vivent dans le cluster.

8. Charts Helm

helm list -A
pluto detect-helm -owide --target-versions k8s=v1.34.0

Pour chaque release, vérifiez que la version du chart supporte la cible : beaucoup de charts déclarent une contrainte kubeVersion dans leur Chart.yaml et refusent de s'installer hors de cette plage. Mettez les charts à jour avant le saut qui supprime l'API qu'ils utilisent. Si une release a été installée avec une API désormais supprimée, Helm ne peut plus la mettre à jour ; le plugin helm-mapkubeapis réécrit les métadonnées de la release pour débloquer la situation.

Après la bascule : mettez à jour kubectl (au plus une version mineure d'écart avec le cluster), les images de CI qui l'embarquent, et notez la prochaine échéance. Un cluster en 1.35 quitte le support standard le 27 mars 2027.

Un sprint à prix fixe, rollback préparé

Si vous préférez que quelqu'un s'en charge : inventaire, répétition sur staging, bascule hors heures ouvrées, rapport. 1 500 € HT pour un saut simple, 2 500 € HT pour un cluster en retard de deux ou trois versions, 3 500 € HT pour un cluster complexe. Non facturé si la bascule échoue dans la fenêtre convenue.

Questions fréquentes

Peut-on passer directement d'EKS 1.31 à 1.34 ?

Non. EKS n'accepte qu'une version mineure par mise à niveau du plan de contrôle : 1.31 vers 1.32, puis 1.33, puis 1.34. Chaque saut demande de mettre à jour les nœuds et les add-ons avant le suivant.

Combien de temps dure une mise à niveau EKS ?

AWS indique plusieurs minutes pour le plan de contrôle. Le remplacement des nœuds et la mise à jour des add-ons prennent davantage, selon la taille du cluster et les PodDisruptionBudgets : mesurez-le sur un staging avant de fixer la fenêtre.

Peut-on revenir en arrière après une mise à niveau EKS ?

Oui depuis juillet 2026, dans les 7 jours, d'une seule version mineure, pour un cluster mis à niveau sur place. Les add-ons et les nœuds non Auto Mode sont à rétrograder séparément. Un cluster mis à niveau d'office en fin de support étendu ne peut pas revenir en arrière.

Les nœuds EKS sont-ils mis à jour avec le plan de contrôle ?

Non, sauf en EKS Auto Mode. Les groupes de nœuds managés, les nœuds autogérés et les pods Fargate existants restent sur leur version tant que vous ne les mettez pas à jour.

Comment trouver les API dépréciées avant une mise à niveau Kubernetes ?

Combinez pluto pour les manifestes et les releases Helm, kubent pour les objets du cluster, et les upgrade insights EKS (aws eks list-insights) pour les appels réellement observés sur 30 jours.
